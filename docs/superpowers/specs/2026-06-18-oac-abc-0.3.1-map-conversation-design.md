# OAC Agent Browser Core 0.3.1 MAP Conversation Integration Design

Date: 2026-06-18
Status: Draft for implementation planning

## Purpose

Open Agent Connect should consume Agent Browser Core `v0.3.1` and provide the
OAC-side host behavior required by the new MAP URI renderer flow.

The motivating user flow is:

1. A user opens a remote Bot Page inside the OAC Browser.
2. The Bot Page shows protocol summaries such as `simplebuzz` and
   `skill-service`.
3. The user clicks a protocol detail or conversation action.
4. ABC resolves and renders the chain-native resource, while OAC only handles
   OAC-owned privileged actions such as opening the local conversation page.

This document is intentionally written as input for a separate implementation
planning session. It defines the product boundary, expected behavior, likely
code areas, and acceptance criteria. It is not an implementation plan.

## Background

Agent Browser Core `v0.3.1` adds the first MAP URI protocol renderer design:

```text
map://simplebuzz/pin/{pinId}
map://skill-service/pin/{pinId}
map://simplemsg/conversation?peer={globalMetaId}
```

MAP links are MetaID Application Pointers. They identify chain-native protocol
objects or protocol actions. They are not OAC routes, IDBots routes, or Web2
renderer URLs.

ABC owns:

- MAP URI parsing and normalization;
- MAN-backed protocol pin resolution;
- latest-effective-version and historic selector handling;
- MAN `content` and `contentSummary` parsing for protocol detail resources;
- first-party renderer selection for `simplebuzz`, `skill-service`, and generic
  protocol pins;
- Browser UI dispatch of trusted host actions.

OAC owns:

- the selected local Bot actor;
- OAC profile and private chat identity state;
- the local conversations page;
- OAC route wrappers around the shared Browser UI;
- mapping host-neutral trusted actions to OAC routes or command handlers.

The key boundary is:

```text
ABC decides what a MAP resource means.
OAC decides whether the current local Bot can perform an OAC-owned action.
```

## Package Consumption Boundary

ABC `v0.3.1` was published as a multi-package release. OAC should consume the
release through its existing package sync scripts instead of manually editing
only one dependency.

OAC currently directly pins these Browser packages:

```text
@openagentinternet/agent-browser-host-contract
@openagentinternet/agent-browser-core
@openagentinternet/agent-browser-ui
@openagentinternet/agent-browser-test-harness
```

The implementation should bump those direct pins to exact version `0.3.1` using
the existing script:

```text
node scripts/bump-agent-browser-core-version.mjs 0.3.1
```

Then verify the pins with:

```text
node scripts/check-agent-browser-core-version.mjs --latest 0.3.1
```

Do not install `@openagentinternet/agent-browser-host-standalone` in OAC. OAC is
an embedded host and already has its own daemon route wrapper. The existing
package sync library explicitly treats the standalone host package as
disallowed in OAC.

The ABC release also includes packages such as first-party renderers and name
resolvers. OAC should receive those through the published ABC dependency graph
unless OAC code has a concrete direct import. If a new direct OAC import becomes
necessary, the package sync script and its tests must be updated in the same
change so future releases cannot drift.

## Goals

- Pin OAC's direct ABC package set to `0.3.1`.
- Let OAC Browser open MAP resources supported by ABC `0.3.1`.
- Serve OAC Browser route wrappers for `/browser/map/...`.
- Add OAC support for the host-neutral `open-conversation` trusted action.
- Expose `message-view` capability for local OAC Bot actors that can view
  conversation history.
- Route conversation actions to the existing OAC conversations UI without
  encoding OAC paths into public MAP links.
- Preserve the selected `peer` in `/ui/conversations?local=...&peer=...`, even
  when no prior conversation row exists yet.
- Keep ABC host-neutral and keep OAC-specific behavior in OAC adapters/routes.

## Non-Goals

- Do not implement standalone private message sending in this OAC milestone.
- Do not add arbitrary third-party renderer execution.
- Do not copy MAP protocol parsing or MAN payload parsing into OAC.
- Do not move OAC private chat storage, signer access, or profile management
  into ABC.
- Do not bind public Bot Page links to `/ui/*` routes.
- Do not add `@openagentinternet/agent-browser-host-standalone` as an OAC
  dependency.
- Do not make an OAC release in this change. Release work can happen after
  implementation is merged and verified.

## User Flows

### Open Buzz Detail

User flow:

1. User opens `metaid://{remoteGlobalMetaId}` in OAC Browser.
2. ABC Bot Page renderer shows a summarized buzz item.
3. The item links to `map://simplebuzz/pin/{pinId}`.
4. OAC route wrapper serves the shared Browser page for `/browser/map/...`.
5. ABC resolves the MAP resource through the configured MAN base URL.
6. ABC renders the full `simplebuzz` detail with text, media, proof fields, and
   version identity.

OAC should not parse the buzz payload or select the buzz renderer.

### Open Skill Service Detail

User flow:

1. User opens a remote Bot Page in OAC Browser.
2. ABC Bot Page renderer shows summarized `skill-service` content.
3. The item links to `map://skill-service/pin/{pinId}`.
4. ABC resolves and renders the service detail.

OAC should only provide Browser runtime, MAN configuration, and route serving.

### Open Conversation From Bot Page

User flow:

1. User opens a remote Bot Page in OAC Browser.
2. The selected Browser actor is a local OAC Bot.
3. The remote Bot Page exposes a conversation action represented by:

   ```text
   map://simplemsg/conversation?peer={remoteGlobalMetaId}
   ```

4. ABC renders that resource as a trusted host action:

   ```text
   open-conversation
   ```

5. ABC Browser UI posts the action to OAC through `/api/browser/actions`.
6. OAC validates the current actor and peer.
7. OAC returns a safe local href:

   ```text
   /ui/conversations?local={localGlobalMetaId}&peer={remoteGlobalMetaId}
   ```

8. ABC UI follows only the safe returned local href.
9. OAC conversations UI opens the requested local/peer thread.

If no prior messages exist, the conversations UI should show an empty selected
thread for that peer rather than redirecting the user to an unrelated first
conversation.

## Trusted Action Contract

ABC `0.3.1` adds the host-neutral trusted action:

```text
open-conversation
```

Expected payload:

```ts
interface OpenConversationPayload {
  conversationUri: string;
  peerGlobalMetaId: string;
  peerName?: string;
  initialComposerText?: string;
}
```

OAC handling rules:

- `peerGlobalMetaId` is required and must be a non-empty string after trimming.
- The local side must come from the selected Browser actor or active OAC profile,
  not from the action payload.
- The payload must not be allowed to choose the local Bot.
- OAC should construct the returned href itself. Do not trust a payload-provided
  href.
- If the actor is missing, has no Global MetaID, or lacks message-view support,
  return `manual_action_required` or the existing OAC command failure shape with
  a clear identity/capability message.
- A successful result should use the Browser trusted action result shape and
  include a local same-origin href in `data.href`.

Recommended successful result data:

```json
{
  "href": "/ui/conversations?local=<encoded-local-global-meta-id>&peer=<encoded-peer-global-meta-id>"
}
```

ABC UI already performs safe-href checks before navigation. OAC should still
return only local paths for this action.

## Runtime Capability Contract

OAC Browser actors currently expose capabilities such as `private-chat`,
`service-call`, and `template-settings`. For ABC `0.3.1`, local OAC Bot actors
that can view conversation history should also expose:

```text
message-view
```

Expected distinction:

- `private-chat` means the actor can send a private message.
- `message-view` means the actor can open or view local conversation history.

This distinction lets ABC show the right disabled/manual-action behavior when a
host can view but not send, or send but not open a history surface.

## OAC Route Contract

OAC must serve the shared Browser page for MAP route paths.

Current OAC route wrappers already serve paths such as:

```text
/browser
/browser/metaid/{id}
/browser/metaapp/{id}
```

This milestone should add:

```text
/browser/map/{protocol}/...
```

The route wrapper should not parse MAP semantics. It only serves the shared
Browser UI so ABC client code can convert the route back to the Browser URI and
resolve it through ABC.

Apply this check anywhere OAC has its own Browser page route wrapper, including
the daemon UI route and any local standalone/dev server path that mirrors Browser
routes.

## Conversation Page Contract

OAC already has a conversations UI that accepts:

```text
/ui/conversations?local={localGlobalMetaId}&peer={peerGlobalMetaId}
```

For Browser conversation actions, this route must behave as a stable deep link:

- Keep the requested `local` value as the selected local Bot when it resolves.
- Keep the requested `peer` value as the selected peer, even when the
  conversation list does not yet contain that peer.
- Fetch messages for the selected local/peer pair.
- If there are no messages, display an empty thread state for that peer.
- Do not automatically switch to the first unrelated conversation just because
  the requested peer is not in the conversation list.

This behavior is important because a user may click `Conversation` on a remote
Bot Page before sending the first message.

Notes for planning:

  must stay aligned with the published ABC host contract types that OAC bridges
  to.
- `src/core/browser/types.ts` and `src/core/browser/botPageResolver.ts` are

  their action unions and normalization so `open-conversation` is not dropped.
- `src/browser/agentBrowserUiBrowser.d.ts` is a local declaration shim. After
  upgrading ABC, check whether the published UI package now provides the needed
  declarations. Remove the shim if it is obsolete; otherwise update it to match
  the current public API instead of masking type drift.

## Testing Scope

The implementation plan should use test-first changes for the behavior it
modifies. At minimum, cover:

- package pin validation for ABC `0.3.1`;
- OAC actor runtime includes `message-view` where expected;
- OAC core bridge accepts and forwards `open-conversation`;
- OAC host adapter returns a local conversation href for a valid
  `open-conversation` action;
- missing actor, missing peer, and actor-without-identity failures;
- `/browser/map/...` serves the Browser page in OAC route wrappers;
- Browser action UI follows the safe returned href for `open-conversation`;
- `/ui/conversations?local=...&peer=...` preserves a peer with no existing
  conversation row.

Useful focused commands after implementation:

```text
npm run build
node scripts/check-agent-browser-core-version.mjs --latest 0.3.1
node --test tests/daemon/oacBrowserHostAdapter.test.mjs tests/daemon/oacBrowserCoreBridge.test.mjs
node --test tests/daemon/browserRoutes.test.mjs tests/daemon/browserUiRoutes.test.mjs tests/ui/browserPageActions.test.mjs
node --test tests/daemon/httpServer.test.mjs tests/ui/conversationsViewModel.test.mjs
```

The implementation plan should decide whether to run `npm run verify` before
merge. Because this change touches package pins and shared Browser integration,
full verification is preferred before merging unless the plan records a specific
reason to rely on targeted tests plus CI.

## Security Requirements

- Do not trust route or href values from MAP action payloads.
- Do not let a remote Bot Page choose the local OAC Bot identity.
- Do not allow `javascript:`, absolute external URLs, or protocol-relative URLs
  to be returned from OAC `open-conversation`.
- Do not expose private chat secrets or signer material to ABC.
- Do not execute chain-declared renderer URLs.
- Keep MAN data parsing inside ABC-provided resolver/renderer code.
- Keep OAC private chat send behavior on the existing `private-chat` trusted
  action path.

## Acceptance Criteria

- OAC direct ABC package pins are exact `0.3.1` and pass the package sync check.
- OAC builds against ABC `0.3.1` without stale local type shims hiding contract
  mismatches.
- OAC Browser serves `/browser/map/simplebuzz/pin/{pinId}` and
  `/browser/map/skill-service/pin/{pinId}` through the shared Browser page.
- MAP protocol pin details are resolved and rendered by ABC, not by OAC-specific
  payload parsing.
- OAC actors that can view messages expose `message-view`.
- `open-conversation` is accepted by the OAC bridge and adapter.
- A valid `open-conversation` action returns a local href to
  `/ui/conversations?local=...&peer=...`.
- Conversation deep links preserve the requested peer even when no prior
  conversation row exists.
- Invalid or unsupported conversation actions return a clear failure or
  manual-action result without navigating.
- ABC core/UI remain free of OAC imports, and OAC changes remain in OAC adapter,
  route, UI, or test code.
