# DSH Plugin Tools and Mechanisms: Cross-Host Portability Assessment

Date: 2026-09-19
Branch: `dsh-tools-portability`
Question: can the tools recently built for the DSH plugin (`metaweb_search`-class
native tools, the dream mechanism, and the memory mechanism) — originally
targeted at DSH — be generalized to the other supported coding-agent hosts
(Codex, Claude Code, OpenClaw, and the other skill-bind hosts)? How fast?

## Verdict

**Yes for the large majority, and faster than it might look.** The DSH plugin
was built CLI-first on purpose: the capability core of every tool is the
host-agnostic `metabot` CLI + OAC daemon, and the plugin is a thin native-tool
shell over it. The porting problem is therefore mostly *exposure*, not
*re-implementation*:

- Of the **58 native tool names** the plugin registers, ~80% map onto `metabot`
  CLI verbs that already exist and run with zero DSH present. Porting them to
  Codex / Claude Code / OpenClaw means writing SKILL.md documents and adding
  them to the per-host skillpacks — the same channel those hosts already use.
- The **dream pipeline is already host-agnostic** (prompts, due/backoff math,
  plan/synthesize/commit writes live in `src/core/memory/dream*`), and a
  complete non-DSH executor already exists: `metabot dream run` drives the whole
  dream through the local-runtime LLM chain (verified at
  `src/cli/runtime.ts:4827-4885`). What is missing is only the **nightly
  trigger**: the unattended tick lives in the DSH plugin
  (`dsh-plugin/src/dream-scheduler.ts`), and no daemon-side dream tick exists.
- The **memory system is ~80% host-agnostic** (stores, injection-XML assembly,
  regex+rule extraction, recall/search, manual `memory transcript append`). The
  DSH-coupled parts are the per-turn **injection hook** (`agent/pre-step` on
  `oac-*` presets) and the post-turn **capture hook** (`session/event`
  `turn/end`), which need per-host equivalents (or an agent-mediated
  approximation through a skill).
- The strongest existence proof: **surf and scheduled tasks already run fully
  headless in the daemon** on auto-discovered local LLM runtimes
  (claude-code/codex/openclaw/… spawned by `LlmExecutor` backends). Unattended,
  tool-using LLM loops with no DSH anywhere are a shipped capability, not a
  design hope.

Three tiers summarize the work (detail below): **Tier A** (SKILL docs only),
**Tier B** (small, contained core/daemon additions), **Tier C** (genuinely
host-coupled; needs per-host design decisions).

## Background: the two host integration models

**Skill-bind hosts (Codex, Claude Code, OpenClaw, zcode, workbuddy — 15
platform ids in `src/core/platform/platformRegistry.ts`, 5 release packs).**
The shared skill source of truth is `~/.metabot/skills/`; `metabot host
bind-skills --host <host>` symlinks `metabot-*` entries into the host's own
skill root (`~/.codex/skills`, `~/.claude/skills`, `~/.openclaw/skills`, …).
Skills are SKILL.md documents that teach the host's agent to call the
`metabot` CLI shim; results come back as `MetabotCommandResult` JSON envelopes
(`success | awaiting_confirmation | waiting | manual_action_required |
failed`). There is **no native tool registration, no hook usage, and no MCP
server** for these hosts today. Skillpacks are generated by
`scripts/build-metabot-skillpacks.mjs` from the hard-coded 16-entry
`METABOT_SKILLS` list (`scripts/build-metabot-skillpacks.mjs:17-34`).

**DSH.** DSH gets the same skill-bind layer (`~/.dsh/skills`) *plus* the Cordis
plugin (`dsh-plugin/`), which adds: ~58 native schema-validated tools, per-Bot
agent presets (`oac-<slug>`), per-turn memory injection/capture observers,
native approval dialogs (`ctx.approval`), the right-sidebar Bot Browser
(iframe + SSE + postMessage), and host-side schedulers (dream, schedule,
group-task worker sessions, chain-history summary).

So the porting target for "DSH tools on other hosts" is precisely: **put the
underlying capability behind a SKILL.md + CLI path that every host already
consumes.**

## The LLM executor chains (why unattended features port)

Three chains, layered:

- **Chain A — DSH in-process `ctx.llm`** (`dsh-plugin/src/llm-generate.ts`).
  DSH-only; used by the plugin's dream runner and host executor.
- **Chain B — daemon host-executor bridge**
  (`src/core/llm/hostLlmExecutorBridge.ts`, `createHostFirstCompletion`):
  the daemon pushes `generate` requests over SSE and a connected DSH host
  executes them. Returns `null` when DSH is absent — by design, so callers
  "fall through to its local-runtime chain unchanged."
- **Chain C — local CLI LLM runtimes** (`src/core/llm/llmRuntimeDiscovery.ts`,
  `LlmExecutor` + backends in `src/core/llm/executor/backends/`): spawns
  claude-code / codex / openclaw / gemini / … as one-shot completion engines,
  with per-Bot bindings. Fully host-agnostic.

Every daemon-side passive feature (surf loop, scheduled tasks, hygiene deep
consolidation, manual `dream run`) already uses **B-then-C**: DSH pair when a
DSH host happens to be connected, else the local runtime chain. DSH is a
priority optimization, never a dependency. This is the load-bearing fact for
porting the dream mechanism.

## Tool-by-tool portability

Tier classification:

- **A — SKILL.md only.** The CLI verbs exist; porting = write/extend SKILL
  docs, add to `METABOT_SKILLS`, regenerate skillpacks, rebind.
- **B — small core addition first** (a new CLI verb or a daemon tick), then A.
- **C — host-coupled.** Depends on a DSH host API with no generic equivalent;
  needs a per-host design decision (or stays DSH-only by intent).

## Mechanisms

### Dream (做梦)

- **Host-agnostic (core):** the entire pipeline — due-date/stagger/backoff
  math, prompts, fragmenting, plan/synthesize/commit/fail writes, summaries,
  self-identity — lives in `src/core/memory/dream{Service,Prompt,Store,Fragments}.ts`
  with the LLM transport **injected** (`dreamService.ts` header states the
  intent explicitly). CLI verbs: `metabot dream
  due|status|plan|synthesize|commit|fail|run|summaries|self-identity|capabilities`.
- **Headless executor already exists:** `metabot dream run`
  (`src/cli/runtime.ts:4827-4885`) = `createHostFirstCompletion` (Chain B,
  180 s) → local runtime resolver + `LlmExecutor` (Chain C). Verified in
  source; errors carry explicit "bind with `metabot llm`" guidance.
- **DSH-coupled:** only the nightly ticker. `dsh-plugin/src/dream-scheduler.ts`
  ticks every 10 min while the DSH host is alive and drives plan → `ctx.llm`
  → commit per fragment (`memory-routes.ts: runDreamWithLlm`), plus the
  pre-dream surf trigger and the hygiene tail. **No daemon-side dream tick
  exists** (verified: no `applyDream`/dream-tick registration in `src/cli/` or
  `src/daemon/`).
- **Port path (Tier B):** add a daemon-side dream tick mirroring the schedule
  tick pattern — for every dream-enabled profile: `dream due` → `dream run`
  (the CLI executor already handles Chain B→C, so DSH-pair-first still wins
  when DSH is open) → hygiene tail → optional pre-dream surf gate. The plugin
  scheduler can then stand down via the same lease trick the schedule
  heartbeat uses, or simply keep ticking (dream commit is idempotent per
  date).

### Memory (记忆)

- **Host-agnostic:** all stores (file-backed, under `~/.metabot/profiles/
  <slug>/`), `buildMemoryBlocksForRequest()` XML assembly (no LLM),
  regex+rule extraction (`memoryExtractor`/`memoryJudge`), recall/search
  verbs, and the manual mirror verbs `memory transcript append/read`. A2A
  private chats are already mirrored daemon-side (`channel:
  'metaweb_private'`).
- **DSH-coupled (the mechanism proper):**
  1. *Per-turn injection* — `dsh-plugin/src/memory-observe.ts
     applyMemoryInjection()` hooks `agent/pre-step` on `oac-*` preset
     sessions, calls `metabot memory blocks`, appends the XML as a
     prefix-cache-friendly synthetic user message.
  2. *Post-turn capture* — hooks `session/event` `turn/end`, slices the turn
     via `session.snapshotEvents()`, then `memory transcript append` ×2 +
     `memory extract`.
  3. *LLM judge / multilingual extraction* — the CLI `memory extract` handler
     wires `judgeComplete`/`llmExtract` to `/api/llm/host-executor/generate`,
     which is DSH-only today; without DSH it degrades to rule-only
     extraction. (Everything else on the daemon falls through to Chain C;
     extract does not — a one-call gap, `src/cli/runtime.ts:4260-4290`.)
- **Port paths, in fidelity order:**
  - *Agent-mediated (Tier A):* a `metabot-memory` skill teaches the host agent
    to pull `memory blocks` at conversation start and to mirror/extract after
    meaningful turns. Zero host dependencies; works on every host; lower
    discipline than hooks (the model can skip it).
  - *Host hooks (Tier C, per host):* Claude Code has a hooks system
    (UserPromptSubmit-class events) that can call the same two verbs; Codex
    and OpenClaw need their own equivalents assessed individually. The verbs
    themselves are done.
  - *Judge fallback (Tier B):* point the extract handler's completion at
    `runLlmPromptWithRuntimeFallback` so the LLM judge lights up without DSH.

### Hygiene, surf, schedule

- **Hygiene:** service fully in core; `memory hygiene run` already uses the
  B→C chain. Only the nightly trigger is DSH-bound → fold into the daemon
  dream tick (Tier B).
- **Surf:** fully host-agnostic execution in the daemon (verified end to
  end: `/api/surf/run` → `SurfService` → `runSurfSessionExecutor` →
  `runSurfTurnWithTools` on Chain B→C). Porting = a skill doc (Tier A).
- **Schedule:** fully host-agnostic (daemon 30 s tick executes all channels;
  DSH's richer "run as a DSH conversation" executor is an optional upgrade,
  coordinated by the heartbeat lease). Skill already ships.

## Cross-cutting translation issues

1. **Approval gates.** DSH tools gate writes behind native `ctx.approval`
   dialogs (skill install/publish, external-file upload, group-task close,
   metaapp publish). On skill-bind hosts the equivalent already exists as the
   agent-mediated confirm contract: `awaiting_confirmation` envelopes plus the
   `confirmation-contract.md` prose injected into every skill ("show the
   provider/price and wait for explicit confirmation"). Semantic parity is
   close; enforcement moves from host chrome to the skill contract.
2. **Native tools vs skill docs.** A SKILL.md port keeps capability parity but
   not UX parity: DSH gets schema-validated function calls from turn 1; other
   hosts get doc-mediated CLI usage. The `search_online_bots` pattern already
   documents the graceful bridge ("prefer the native tool when available in
   this session's function list, fall back to the CLI"). If native-tool parity
   ever becomes a requirement, an **MCP server** exposing the metabot verbs is
   the natural next channel — none exists today (verified), so it is a new
   build, not a port.
3. **In-process reads.** Several DSH tools call OAC core directly
   (`local-read.ts` seam) for speed. Other hosts don't need this — they go
   through the CLI/daemon, which is the canonical path. Formatting is already
   shared (`src/core/metaweb/format.ts` is used by CLI, DSH tools, and
   skillpack alike).
4. **Persona/preset projection.** DSH projects the Bot persona into `oac-*`
   presets; the codex host has persona projection into `~/.codex/AGENTS.md`
   (`src/core/host/hostPersonaProjection.ts`, codex-only). Extending persona
   projection to claude-code/openclaw is a separate, already-scoped gap — not
   required for tool porting, but required for the full "Bot on another host"
   experience.

## Recommended phasing

**Phase 1 — exposure (doc-only, fastest payoff).** Write SKILLs for the
Tier A families that lack them: `metabot-qanda`, `metabot-protocol`,
`metabot-surf`, `metabot-media`, `metabot-memory`, `metabot-knowledge-base`,
`metabot-simplenote`, `metabot-grouptask`, twin read-side (fold into a
`metabot-twin` doc or the memory doc), `chainhistory recall` (fold). Add them
to `METABOT_SKILLS`, regenerate packs, rebind hosts. This alone takes the
recent DSH tool wave (Q&A, protocol registry, surf, media, KB) to every host.
English + Simplified Chinese coverage for any user-facing copy, per repo
rules.

**Phase 2 — close the small core gaps.** (a) daemon-side nightly dream +
hygiene tick (schedule-tick pattern); (b) `memory procedure *` CLI verbs;
(c) `knowledge-base study *` CLI verbs; (d) extract-LLM-judge fallback to
Chain C. Each is contained; all reuse shipped executors.

**Phase 3 — per-host integration decisions.** Memory injection/capture via
host hooks (Claude Code first — it has a hooks system; assess Codex/OpenClaw
individually), twin delegation on daemon `LlmExecutor` sessions, and
(optionally) an MCP server if native-tool UX parity becomes a requirement.

## What this assessment did NOT verify

- Runtime behavior on an actual Codex/Claude Code/OpenClaw install (static
  code reading only; no end-to-end run of a ported skill was performed —
  nothing was ported yet).
- Exact Codex/OpenClaw hook capabilities for Phase 3 (Claude Code hooks were
  not examined in depth either; that is Phase 3 homework).
- Cost/quota behavior of the media relay and chain writes from other hosts
  (mechanisms are identical, but usage patterns will differ).
